# Project Scope

## 1. 项目背景

传统规则式电商客服通常依赖关键词匹配和固定话术，面对多轮对话、表达歧义、复杂售后问题和不断变化的业务知识时，维护成本较高。

大语言模型可以提升自然语言理解和回复生成能力，但直接调用大模型仍然存在知识过时、回答不可追溯、业务操作不可靠和数据安全等问题。

本项目计划结合以下技术解决这些问题：

- 使用 RAG 检索企业知识并提供答案来源
- 使用 Agent 调用订单、物流、退款等业务工具
- 使用意图识别和情感分析辅助路由与风险判断
- 使用离线评测验证系统效果
- 使用微调和量化探索专用模型的训练与部署

本项目定位为面向生产场景设计的学习型工程项目，而不是已经投入生产的商业系统。

## 2. 目标用户

### 消费者

消费者希望快速获得准确、清晰且与当前订单状态相关的答案，包括商品信息、物流进度、售后政策和退款流程。

### 人工客服

人工客服希望系统能够自动处理重复问题，并在转人工时提供完整的会话摘要、用户诉求、情绪状态和已执行操作。

### 客服主管

客服主管希望查看会话数量、问题类型、解决率、转人工原因、投诉风险和知识库缺口，以便改进客服流程。

### 系统管理员

系统管理员负责维护知识库、业务工具、模型配置、用户权限和审计记录。

## 3. 核心业务场景

### 商品咨询

回答商品属性、规格、使用方式、库存和适用场景等问题。

### 订单查询

根据经过校验的用户身份和订单编号查询订单状态。

### 物流查询

查询发货状态、物流节点和预计送达信息。

### 售后政策问答

从知识库检索退换货条件、保修范围、运费规则和处理时限，并提供来源引用。

### 退款申请

识别退款意图，收集订单号、退款原因等必要参数，并调用模拟退款工具。系统不执行真实资金操作。

### 投诉风险识别

结合情感分析、关键词和对话上下文识别强烈不满、重复投诉和升级风险。

### 人工转接

在低置信度、高风险、用户明确要求或工具执行失败时转接人工客服，并生成会话摘要。

## 4. 第一版范围

第一版以完成可测试的端到端业务闭环为目标，包括：

- FastAPI 后端基础工程
- Vue 3 基础聊天页面
- 用户、会话和消息的数据模型
- 可替换的大语言模型服务接口
- 多轮对话记录
- 基础意图识别和情感分析
- 真实的文档入库与向量检索
- 基于知识库的回答和来源引用
- 合成订单、物流和退款数据
- 订单查询、物流查询和退款申请工具
- Agent 工具选择与执行
- 人工转接规则
- 固定离线评测集
- 自动化测试和 Docker Compose 部署

## 5. 后续扩展范围

第一版业务闭环稳定后，再逐步增加：

- 中文意图分类模型训练
- 情感分类和投诉风险模型训练
- Embedding 和 Reranker 优化
- 客服对话数据清洗与 SFT 数据构造
- LoRA/QLoRA 微调
- 模型量化
- 私有化推理服务
- 模型注册与版本管理
- 灰度发布和用户反馈闭环
- 客服运营分析看板

## 6. 暂不实现

为了控制项目复杂度，当前阶段暂不实现：

- 真实支付、扣款或资金退款
- 真实电商平台生产账号接入
- 未经授权的用户数据采集
- 大规模基础模型预训练
- 多租户计费系统
- 高可用集群和跨地域容灾
- 自动批准高风险售后操作
- 完全替代人工客服
- 基于未经验证数据得出的业务收益声明

## 7. 技术目标

### 可维护性

- 在线应用、知识库处理和模型训练相互隔离
- 外部模型、向量数据库和业务系统通过接口抽象
- 配置与代码分离
- 核心模块具有自动化测试

### 可靠性

- 工具参数必须经过结构化校验
- 修改业务状态的操作需要幂等机制
- 工具执行过程需要保留审计记录
- 外部服务失败时提供明确的降级策略
- 低置信度问题能够拒答、澄清或转人工

### 可评测性

- 建立固定且版本化的评测集
- 分别评估检索、生成、意图识别和工具调用
- 每次重要改动后运行回归测试
- 评测结果保留模型、配置和数据版本信息

### 可部署性

- 支持通过环境变量切换模型服务
- 支持 OpenAI 兼容的模型接口
- 支持 Docker Compose 本地运行
- 在线服务与训练任务使用独立环境
- 模型权重和训练产物不进入 Git 仓库

## 8. 初始验收指标

以下数值是项目目标，不是当前已经取得的结果。完成基线评测后可以根据实际情况调整。

### 数据集

- 第一版至少建立 100 条固定测试问题
- 每个核心业务意图都必须包含正常、歧义和异常样本
- 测试集不得与训练集重复
- 所有订单和用户信息均使用合成数据

### RAG

- 使用 Recall@K 评估相关文档召回情况
- 第一版以 Recall@5 不低于 0.85 为目标
- 知识库类回答必须返回可追踪的文档来源
- 知识库无相关内容时不应编造政策或业务规则

Recall@5 的定义为：

相关证据文档出现在前 5 个检索结果中的问题数量，除以全部知识库测试问题数量。

### 意图识别

- 使用 Accuracy、Macro Precision、Macro Recall 和 Macro F1 评估
- 单独报告每个意图的召回率
- 不只使用总体准确率描述效果
- 对低置信度结果执行澄清或转人工策略

### 实体抽取

- 使用 Precision、Recall 和 F1 评估
- 重点评估订单号、商品名称、时间和退款原因
- 错误格式的订单号不得直接传给业务工具

### 工具调用

- 使用固定测试用例统计工具选择正确率
- 使用参数校验通过率和执行成功率评估可靠性
- 第一版以合成业务场景下工具执行成功率不低于 0.95 为目标
- 重复请求不得导致重复退款申请或重复工单

### 人工转接

评测以下场景是否正确转人工：

- 用户明确要求人工服务
- 连续多次无法理解用户问题
- 强烈负面情绪或投诉风险
- 工具执行失败
- 涉及超出机器人权限的业务操作

### 自动化测试

- 核心业务模块必须具有单元测试
- API、数据库和工具调用必须具有集成测试
- 每次提交前运行格式检查和测试
- 后续使用 CI 自动执行测试

## 9. 数据与安全

### 数据来源

项目仅使用：

- 公开且许可证允许使用的数据
- 自行编写的知识库文档
- 自动生成或人工构造的合成订单数据
- 经过脱敏和授权的数据

### 隐私保护

不得提交或公开：

- 真实姓名
- 手机号
- 收货地址
- 身份证信息
- 真实订单号
- 聊天账号
- API Key
- 数据库密码
- 未脱敏客服对话

### 工具安全

- 查询订单前需要验证用户与订单的关系
- 修改状态的工具需要权限检查
- 高风险操作需要人工确认
- 所有工具调用保留输入、结果、时间和状态
- 日志不得记录完整敏感信息

### 模型安全

- 将用户输入和知识库内容视为不可信数据
- 防止提示词注入改变系统权限
- 不允许模型绕过工具校验直接修改业务数据
- 对模型输出进行必要的格式和内容检查
